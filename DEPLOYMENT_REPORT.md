# ZorkSec Deployment Report

Covers the self-extracting installer, offline-asset guarantee, and the
"deployed files exactly match repository source" invariant.

## Installer (`install.sh`)

- Generated by `build_installer.py` from the tested source tree (base64 blobs,
  unique per-file decoding). Recreates `/opt/zorksec`, a venv, the `zorksec`
  command (+ `tools` alias), DB init, default user.
- **96 files embedded, ~1.99 MB** (grew from the vendored offline assets).
- **In-sync invariant enforced by a test:**
  `tests/test_installer.py::test_committed_install_sh_is_in_sync_with_source`
  fails CI if any embedded blob differs from disk — preventing the
  "deployed instance differs from the repo" failure class. Current status: **0 stale**.
- Ubuntu/Debian venv fix retained (installs version-specific `python3.x-venv`,
  fails loudly with the exact apt command).

## Offline / no-CDN guarantee (air-gapped Kali)

All previously CDN-hosted assets are now vendored under
`zorksec/web/static/vendor/` and referenced via `url_for('static', ...)`:

| Asset | Local path |
|-------|-----------|
| xterm.js / fit addon / CSS | `vendor/xterm.min.js`, `vendor/xterm-addon-fit.min.js`, `vendor/xterm.min.css` |
| socket.io client | `vendor/socket.io.min.js` |
| Font Awesome (CSS + 3 woff2) | `vendor/fontawesome/...` |
| Web fonts (Inter/JetBrains Mono/Orbitron, 14 woff2) | `vendor/fonts/fonts.css` + `vendor/fonts/f*.woff2` |

**Verification:** `grep "https://"` across all templates returns **zero**
external references; `fonts.css` contains no `gstatic`/`googleapis` URLs. Locked
in by `test_frontend_assets_are_vendored_offline`, `test_fonts_vendored_offline`,
and `test_terminal_assets_served_locally_not_cdn`.

The only remaining matches for "cdn" live **inside** the minified xterm/socket.io
library files (their own sourcemap/homepage comments) — not runtime loads.

## Static assets, routes, templates

- Cache-busting `?v=<mtime>` on `zorksec.css`, Font Awesome, fonts, and all
  page JS, so an upgrade can never serve a stale cached bundle.
- External JS bundles: `zorksec-ui.js` (all pages), `dashboard.js`,
  `kali_diagnostics.js`, `diagnostics.js` — all serve `200` with a JS content type.
- Themed error pages (`error.html`) wired to 400/403/404/500 handlers; 500s log
  a stack trace + reference id (no raw Internal Server Error).

## Database initialisation

- SQLite WAL mode, `busy_timeout=15s`, additive migrations for the recovery-
  question columns (idempotent `ALTER TABLE ADD COLUMN`).
- Background health refresh now commits per tool (no long write transaction
  across network I/O) — eliminates `database is locked` under concurrency.

## Post-deploy smoke checklist (run on a real Kali desktop)

1. `sudo bash install.sh` → `zorksec --web`.
2. Log in `zorksec/zorksec` → complete wizard (password + recovery question).
3. Dashboard renders with icons/fonts **with networking disabled**.
4. Click Install / Run / Docs on Nmap → terminal tab opens and streams output.
5. Run on a service tool (e.g. MISP) → modal guides to Docs (no dead-end).
6. Kali Diagnostics → Run Scan / Auto Repair respond.
7. Log out → confirm `/`, `/terminal`, `/api/*` redirect to `/login`.
8. Forgot password → answer question → reset → log in.
